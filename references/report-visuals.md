# 报告图表：先问题，再事实，再呈现

本文件是可配置默认风格。用户自己的报告框架和品牌要求优先。

## 主图：开发交付全流程

顶部交代组织前提：谁管人、谁按交付组织。接着画需求来源/pitch → 评审与资源 → 方案/验收条件 → 执行 → 集成 → Eval/测试 → 发布 → 观察与维护。每个阶段至少能解释：输入、执行者、动作、产出、交接、验收责任；人数、耗时、等待、工具和失败路径有证据才写。

按实际材料拆简单/复杂、可解耦/强依赖分支；平行泳道体现并行工作，合流明确由谁集成，失败箭头返回具体修复节点。灰度、正式发布、客户验收区分。不同任务的时间不能拼成承诺或画成比例尺。

## 个人工作时间与工具

- 有可靠占比/时长：用分配条或时间线，注明周期、分母、范围和是否估计；相互重叠的活动不要画成总和100%。
- 只有定性材料：用活动卡片，按创造性工作、沟通协调、事务性工作或本次适用维度分组。
- 每种活动连接实际平台和操作：工具 → 在何时做什么 → 形成什么产出/交接；避免孤立工具Logo墙。
- 时间未知标待补，不能为了凑满一天制造数字；作息不等于人效。

## 结构与语言

一图一句结论，模块同层同粒度，节点使用“角色＋动作＋产出”或平行短句。比较表首列是简洁标签，无bullet；其余列用“短加粗标签＋完整事实句”，通常1–3条，每条尽量两行内。按职责/机制/周期/异常固定顺序比较，不让一个单元格承担整段叙事。

重点图使用语义颜色，默认：暖白底、深蓝标题、深色正文；浅蓝=需求/决策/主干，浅绿=执行/验收/观测，浅橙=等待/返修/估计。把这组颜色写进本任务 plan.style_budget，图型参数是参考，不是不可覆盖模板。辅助图使用灰白/深蓝矩阵或卡片，少量强调即可。不要给每个节点随机分配颜色。

关键数字/名词链接对应证据，不整句变蓝。来源和完整链接可放画板下方的文档段落，图中用短证据ID，避免长URL撑破节点。

## 事实与视图分离

任务内维护 facts、evidence、gaps、visuals 的稳定ID；章节、图型和颜色单独配置。同一事实变化后更新所有引用它的摘要、表格、主图。只重排目录时不改原来源锚点。复用原图须核实适用范围，合并重复图时检查所有独有信息是否保留。
