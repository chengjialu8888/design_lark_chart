# 画系统泳道图

横向按**执行阶段**排，纵向按**系统或参与方**分泳道。用带说明的箭头连起实际的动作。读者看图就能知道谁来做、先做什么、传了什么、在哪里分开。

## 先核对实际流程

1. 从真实入口往下查，找到产生任务的一方、执行的一方、外部调用、存储和结果。字段名和判断条件以代码或用户提供的规格为准。遇到运行时开关，区分代码里的设计与已核实的部署或执行结果。
2. 把主流程归纳为几个短阶段。逐条写明箭头从哪到哪、传什么、什么时候传。区分请求与返回、数据库里保存的事实与当前配置，以及业务动作成功与记录状态更新。
3. 找到确切的分叉条件。分叉前共用的步骤只画一次，分叉后把对应环节对齐。两条线确实汇合或共用接口时再画连接。等待、重试、人工核对和失败分支按当前问题取舍。

画数据血缘时，先把「输入表 → 加工或同步任务 → 产出表 → 实际读取方」逐段接好。同一张表供多个任务使用，就从这张表分叉，每条箭头写各自用途。图内标真实表名和能帮助定位的任务标识，证据有缺口时只画已核实的直接关系。

## 怎么画

| 图中元素 | 写什么 |
| --- | --- |
| 阶段列 | 用编号和简短动作作标题。阶段多或边界不清时，用不同颜色的标题和同色细虚线外框贯穿各泳道。框和列边界之间留出空隙。 |
| 系统泳道 | 左侧写系统或参与方名称、职责，以及相关资源的真实名称。行用低饱和底色，允许同一灰调，靠明显的明暗差分开相邻行。列的阶段色可以更鲜明，与行底色拉开色相或饱和度。没有动作的格子留空。 |
| 动作框 | 一个动词加一个对象，只补读者需要的信息。若框左侧用彩色竖条指示阶段，同列竖条与列标题、阶段外框同色。色条没有明确用途时，省掉它。 |
| 数据箭头 | 从具体动作框指向另一个动作框，线旁标数据或用途。数据血缘默认用实线表示生产、写入和同步，用虚线表示消费读取或查询，并在图例中说明。线很多时先留走线区，再排节点。 |
| 分支 | 让分叉点和条件看得见，对应步骤对齐。用文字标出分支名，颜色起辅助作用。 |
| 字段细节 | 需要解释数据库读写时，把实际表名放在存储泳道左侧，在相应阶段嵌入小表格。数据血缘把真实表名写进数据节点，作为优先加粗的信息。 |

改图时沿用这套层次。用户只要求改配色、箭头或间距时，保留已核实的流程内容。只调整用户指出的部分，以及因此需要修正的连接。只保留当前任务相关的异常说明。

### 数据库小表格

- 读和写分开标。左列写「字段」，右列按用途写「怎么筛」「用来做什么」或「存什么」。需要核对时，保留真实列名、比较运算、状态值和 JSON 路径。代码属性名与数据库列名不同时，标明对应关系。
- 用人话解释容易混淆的字段，例如「最早什么时候能领」和「领走以后多久有效」，或「数据库只登记一次」和「重试时让外部系统识别同一个请求」。
- 一个状态可能代表不同结果时，一起标出记录类型和可核实的结果。画到期或异常时，说明下一步怎样处理、是否可以再尝试。
- 让主流程最醒目。只用少量强调色标容易误读的关键规则，例如用红字标出两种不同的到期处理。

## 出图与核对

按用户指定的平台和格式交付。简单静态流程可以用 Mermaid。需要稳定的泳道布局、内嵌小表和直角走线时，选能控制坐标和文字的方式，例如 HTML/SVG、绘图画布或用户指定的可编辑画图工具。需要参考配色、箭头或审图时，读 [布局与审图指南](references/layout-and-review.md)。

读者说图乱、文字多、看不出分叉，或要求标字段和判断条件时，先用 [正例、反例与原因](references/examples-and-counterexamples.md) 找到对应问题，再做针对性修改。示例中的字段只用于说明画法，实际图里的表名、字段和值从当前材料核对。

打开渲染结果，先按正常阅读尺寸看全图，再放大文字最密的地方。沿主线和每条分支走到结果，核对箭头方向、先后关系、表名、字段和值。检查相邻泳道底色、同列竖条与标题是否对应、文字有没有溢出，以及去掉颜色后是否还能靠标签分清路径。修正可见问题后再交付。能直接展示就把图放在回复里，来源或版本会影响理解时一并标出。
